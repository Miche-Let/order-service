# 📊 [Order Service] 비동기 Saga 아키텍처 및 대용량 조회 성능 최종 검증 리포트 (3차 부하테스트)

본 문서는 이전 2.5차 테스트에서 발견된 '카탈로그 서비스 동기 조회 병목(풍선 효과)'을 **Redis 단건/목록 캐시 무효화 패턴**으로 해결한 후의 최종 주문 생성(Write) 성능과, 100만 건 이상의
대용량 데이터 환경에서 **복합 인덱스**를 통한 주문 내역 페이징 조회(Read) 성능을 종합적으로 검증한 리포트입니다.

---

## 1. 주문 생성(Write) 성능 최종 검증: Redis 연동을 통한 병목 해소

> **테스트 목적:** 카탈로그 옵션 단건 검증 로직에 Redis 캐시(`product_detail_cache`)를 적용한 후, 이전 모킹(Mocking) 시뮬레이션에서 확인했던 순수 비동기 인프라의 처리량(373
> TPS)을 실제 연동 환경에서도 달성할 수 있는지 검증합니다.

### 📌 부하테스트 타격 결과 (JMeter)

- **부하 규모:** 100 Threads 동시 요청 (총 1,000건 스파이크)
- **측정 결과 (카탈로그 Redis 캐시 연동 후 최종):**
    - **처리량(Throughput):** `424.8 / sec` **(2.5차 모킹 시뮬레이션 대비 113% 달성)**
    - **평균 지연 시간(Average):** `110.3 ms` **(2.5차 모킹(197ms) 대비 추가 44% 단축)**
    - **최소 / 최대 지연 시간 (Min/Max):** `8 ms` / `596 ms`
    - **에러율(Error %):** `0.0%`

### 🔍 아키텍처 병목 해소 분석

이번 424.8 TPS 달성은 MSA 환경에서 발생한 전형적인 '풍선 효과'를 효과적으로 해소했음을 의미합니다.
기존 오더 서비스는 카탈로그 서비스의 MongoDB Disk I/O 한계로 인해 대기 상태에 빠져 있었습니다. 하지만 카탈로그 조회 API에 Redis Cache-Aside 패턴을
적용함으로써, 오더 서비스의 Feign Client 통신 지연 시간이 수 밀리초 단위로 급감했습니다. 결과적으로 오더 서비스는 외부 병목에서 해방되어, 설계해 둔 **Kafka 기반 비동기 파이프라인의
순수 쓰기 성능(424.8 TPS)을 발휘**하게 되었습니다.

### 📈 주문 생성 성능 진화 요약 (TPS 및 지연 시간 변화)

| 지표               | 1차 (DB 락 병목) | 2차 (인벤토리 비동기 분리)  | 2.5차 (카탈로그 모킹) | 3차 최종 (Redis 적용 완료) |
|:-----------------|:-------------|:------------------|:---------------|:--------------------|
| **Throughput**   | 약 30~50 TPS  | 31.5 TPS *(풍선효과)* | 373.9 TPS      | **424.8 TPS ✅**     |
| **Average Time** | 수천 ms        | 2,990 ms          | 197 ms         | **110.3 ms**        |
| **Max Time**     | Timeout 다수   | 7,381 ms          | 858 ms         | **596 ms**          |

## 2. 대용량 주문 조회(Read) 성능 검증: 복합 인덱스(Composite Index) 최적화

> **테스트 목적:** 100만 건의 더미 주문 데이터가 적재된 환경에서, 특정 유저의 '주문 내역 최신순 페이징 조회' 시 테이블 풀 스캔(Full Scan)이 발생하지 않고 즉각적인 응답이 가능한지 DB 실행
> 계획을 통해 검증합니다.

### 📌 PostgreSQL 실행 계획 (EXPLAIN ANALYZE) 결과

적용된 복합 인덱스: `idx_order_user_id_reserved_date` (user_id + reserved_date DESC)

### 🔍 조회 성능 최적화 분석

1. **Index Scan 적중 및 풀 스캔 방어:** 100만 건이라는 대규모 데이터 환경에서도 옵티마이저는 테이블 전체를 뒤지는 풀 스캔(Seq Scan)을 선택하지 않고, 설계된 복합 인덱스(
   `idx_order_user_id_reserved_date`)를 이용한 `Index Scan`을 정확히 수행하여 불필요한 I/O를 차단했습니다.
2. **빠른 응답 시간(Execution Time):** 실제 데이터베이스에서 조건에 맞는 데이터를 탐색하고 `Limit 10`으로 페이징하여 최종 반환하는 데 소요된 시간이 불과
   `1.192 ms`였습니다. B-Tree 인덱스 특성상 데이터가 수백만 건으로 늘어나더라도 응답 시간이 크게 늘지 않고 일정 수준을 유지할 수 있음을 의미합니다.
3. **메모리 버퍼 효율성:** `Buffers: shared hit=7 read=6` 지표가 보여주듯, 물리적인 디스크 읽기(`read=6`)를 최소화하는 동시에 PostgreSQL의 메모리 버퍼 캐시(
   `shared hit=7`)를 효과적으로 활용하여 데이터를 고속으로 반환하고 있음을 확인했습니다.

## 💡 최종 결론 및 회고

Miche-Let 프로젝트의 '주문 처리 파이프라인' 고도화가 완료되었습니다.

- **쓰기(Write) 측면:** 기존의 무거운 동기식 분산 락 구조를 걷어내고, Kafka 기반의 비동기 메시징 아키텍처(Choreography Saga 패턴)를 도입하여 동시성 경합
  상황에서도 에러율 0%와 **424.8 TPS**라는 안정적인 대용량 트래픽 수용력을 확보했습니다.
- **읽기(Read) 측면:** 실제 비즈니스 쿼리 패턴을 분석하여 최적의 DB 복합 인덱스를 설계함으로써, 100만 건 고부하 환경에서도
  **1ms 대**의 빠른 페이징 조회 속도를 달성했습니다.

결과적으로 시스템은 대규모 선착순 트래픽(쓰기 폭주)과 지속적인 데이터 누적 상황(읽기 부하) 모두를 견고하게 방어해 낼 수 있는 분산 아키텍처 모델로 진화했습니다.
