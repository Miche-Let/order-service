# 📊 [Order Service] TO-BE 아키텍처 쓰기 성능 및 가용성 리포트 (2차 부하테스트)

본 문서는 Redisson 분산 락, 트랜잭션 분리(OrderStore), 그리고 Outbox 패턴을 도입한 후의 **시스템 안정성(Write)과 장애 복구 능력**을 실제 수치와 로그로 증명한 2차 성능 테스트
리포트입니다.

---

## 1. 주문 쓰기(Write) 안정성 향상 및 동기식 통신의 한계 도출

> **테스트 목적:** 1차 테스트에서 발생했던 DB 낙관적 락 경합 한계(429 에러)를 해결하기 위해 분산 락을 적용하고, 부하 상황에서의 안정성 및 한계점을 분석함

### 🧪 Test Scope / Conditions

- **환경 어댑터:** `PerfReservationValidationAdapter` 사용 (외부 Reservation 서비스 우회)
- **실제 호출 타겟:** `Inventory Service` (Redisson 분산 락 기반 재고 선점 대기열 제어)
- **HikariCP 설정:** `maximum-pool-size: 10`, `connection-timeout: 5000ms`
- **트랜잭션 동작:** `OrderStore` 계층을 통해 DB 반영 로직을 별도 트랜잭션으로 격리. 외부 서비스 락 대기 중 DB 커넥션 점유를 방지

### 📌 JMeter 타격 결과 (Summary Report)

- **요청 API:** `POST /api/v1/orders`
- **부하 규모:** 100 Threads 동시 요청 (총 1,000건, 10 Loop 스파이크 테스트)
- **결과 요약:**
    - **평균 지연 시간(Average):** `3,003ms` (약 3.0초)
    - **최대 지연 시간(Max):** `7,687ms` (약 7.6초)
    - **에러율(Error %):** `0.0%` (1차 0.2% 예외 발생 -> 0%로 방어 성공)
    - **처리량(Throughput):** `30.9/sec`
- **분석 및 한계 도출:** Redisson 분산 락을 통해 1,000건의 동시성 요청을 순차 큐잉하여 **커넥션 고갈 없이 에러율 0**의 안정성을 확보했습니다. 그러나 동기식(Feign) 통신으로 인해 타
  서비스의 락 획득을 기다리는 동안 오더 서비스의 쓰레드가 점유(Blocking)되어, **목표 처리량(200 TPS)에 크게 못 미치는 30.9 TPS의 물리적 한계**와 최대 7초의 응답 지연이 발생했습니다.
  이는 동기식 락 제어의 명확한 트레이드오프로, 아키텍처의 근본적인 체질 개선이 필요함을 시사합니다.

## 2. 카오스 엔지니어링 및 최종 일관성(Eventual Consistency) 증명

> **테스트 목적:** 외부 서비스(Inventory)가 다운된 장애 상황에서도 오더 서비스의 비즈니스 로직(주문 취소)이 중단되지 않으며, 복구 시 연관된 모든 마이크로서비스의 데이터가 동기화되는지 검증함

### 📌 장애 복구 타임라인 (Saga & Outbox Pattern 로그 분석)

- **테스트 시나리오:** 주문 취소 API 호출 직전, 연동된 Inventory 서비스 프로세스를 강제 종료(Kill)하여 통신 단절 장애 상황 시뮬레이션
- **타임라인 분석:**
    1. **`18:43:46` (정상 응답):** Inventory 중단 상태에서 주문 취소 수행. Order 서비스는 장애 전파 없이 클라이언트에게 즉시 정상 응답을 반환하고 Outbox에 이벤트를 적재함.
    2. **`18:43:49` (비동기 위임):** Kafka 브로커로 이벤트 전송 성공. 타 서비스 장애와 무관하게 이벤트 발행 트랜잭션을 조기 종료함(상태: `PUBLISHED`).
    3. **`18:45:01` (서비스 부활):** 약 1분 15초 후 다운되었던 Inventory 서비스 재기동 완료.
    4. **`18:45:04` (지연된 이벤트 소비):** Inventory가 부팅 직후 Kafka에 보류되어 있던 복구 메시지를 수신하여 재고 원복 완료.
    5. **`18:45:06` (동기화 완결):** Catalog 서비스까지 이벤트를 수신하여 MongoDB 내 읽기 전용 재고 데이터를 업데이트함.
- **결론:** 노드 장애가 전체 시스템으로 전파되지 않는 완벽한 장애 격리(Fault Tolerance)를 달성했으며, 시스템 복구 시 데이터 유실 없이 자동 동기화(Eventual Consistency)가
  완결되는 견고함을 증명했습니다.

## 💡 종합 결론 및 향후 작업방향 (3차 최종 최적화 기획)

1. **[목표 미달성 분석] 동기식의 한계 돌파:** 2차 테스트를 통해 쓰기 안정성(Error 0%)은 확보했으나, 동기식 락 대기로 인해 목표 처리량(200 TPS 이상)에 크게 미달하는 30.9 TPS의
   물리적 한계를 확인했습니다. 이를 근본적으로 해결하기 위해 후속 작업(비동기 큐 전환 이슈 연동)으로 아키텍처를 개선합니다.
2. **주문 생성 비동기 전환 (Event-Driven):** 요구사항인 **200 TPS 이상 확보 및 지연시간 최소화**를 위해, 주문 생성 로직의 Feign 통신을 제거하고 **Kafka 기반의 비동기 메시지
   큐** 방식으로 전면 리팩토링합니다. (Order는 대기 상태만 저장 후 즉시 응답, Inventory가 큐를 소비하며 순차 처리)
3. **읽기 성능 최적화:** 카탈로그 데이터 조회를 위한 **Redis Cache-Aside 패턴** 도입 및 주문 내역 조회용 복합 인덱스를 적용하여 Read 병목(디스크 I/O)을 제거합니다.
